# CopyQmac Documentation

## Cross-Device Sync Phased Delivery Plan

Cross-device data synchronisation between macOS and Fedora via Syncthing is structured into two deliberate phases:

### Stage 1: Read-Only Import and Dry-Run Writer

The initial phase delivers safe data ingestion and tooling:
- **Read-only sync folder import**: Safely reads itemsync folders and maps items to the single tab whose exact configured `syncFolder` matches. A folder claimed by more than one tab is logged and skipped. When no tab claims a manually imported folder, a new tab with empty `syncFolder` may still be created. Repeats are deduplicated first by sync stem and then by content fingerprint.
- **Batch configured sync folder import**: Imports all tabs with configured `syncFolder` paths via menu and status menu actions ("Import Configured Sync Folders"), skipping ambiguously claimed folders with a diagnostic and isolating per-tab errors so all configured tabs are attempted.
- **CopyQ `.cpq` archive import**: Retained specifically for manual backup recovery, allowing historical `.cpq` backup archives to be imported into tabs safely.
- **CopyQ `.cpq` archive export**: File and status menu ▸ "Export Backup…" and File ▸ "Export Current Tab…" write a CopyQ-compatible v4 archive (the layout CopyQ itself writes without an encryption key) to the path chosen in a save panel, off the main thread. Each native pasteboard flavour is written under the CopyQ MIME name for the same payload (`text/plain`, `text/html`, `text/rtf`, `image/png`, `text/uri-list`), other types keep their own identifier without leaking private sync bookkeeping flavours, payload bytes stay unchanged, and notes, pins, tab order and capture times round-trip through the reader. Importing the archive restores those entries; an entry whose content already exists in the tab is skipped as a duplicate, so a repeated payload keeps only its first capture. A capture that carried several pasteboard items (for example copying two images) backs up only the first item's flavours, while multi-file copies keep every path in `text/uri-list` (splitting such captures is a follow-up). Duplicate tab names are disambiguated as "Name (2)", "Name (3)", … and reported. A destination inside a configured tab sync folder or a Syncthing folder is allowed and reported as syncing to the other devices.
- **Dry-run writer**: Validates format conversion and writes CopyQ itemsync directory trees strictly into safe scratch directories, protected from touching real CopyQ, Syncthing directories, or configured tab sync folders (case-insensitive on macOS).
- **CopyQ MIME format enrichment**: Imports translate CopyQ MIME flavour names (`text/plain`, `text/html`, `text/rtf`, `image/png`) to the native macOS pasteboard types (`public.utf8-plain-text`, `public.html`, `public.rtf`, `public.png`) before storing, so an item synced from Fedora displays as rich text and pastes back with its formatting. Unknown MIME types keep their names and bytes. One shared table (`CopyQSyncBridge.flavourNameMappings`) drives both import and export, so a round trip restores the original flavours. Paste-back still enriches any MIME-named flavours left by older imports, without leaking private sync bookkeeping flavours.

### Stage 2a: Live Capture Write-Back

The write-back phase delivers safe, asynchronous writing of macOS clipboard captures into mapped sync folders:
- **Live capture write-back**: Writes newly captured macOS clipboard entries directly into configured tab sync folders off the main thread, adhering to CopyQ's UTC timestamp naming conventions (`copyq_yyyyMMddhhmmsszzz.*`).
- **Collision bumping**: Resolves file stem collisions by advancing timestamps in 1 ms increments until an unused stem is found, ensuring existing files are never overwritten.
- **Capture writes**: Stages every file of a new group under a temporary name and renames the group into place, records the stem with the entry id, and never modifies another item's files. Content and metadata edits rewrite the entry's own group (see Stage 2d below). User deletions are handled by the separate two-way deletion stage.
- **Safety boundaries**: Strictly blocks writes to upstream CopyQ application support, configuration, or archive paths.
- **One deliberate off switch**: A tab with a non-empty `syncFolder` always writes and always watches. There is no master write-back toggle and no per-tab write-back or watch toggle; only "Pause Sync" / "Resume Sync" in Preferences, the File menu, and the status-bar menu stops both directions.
- **Bounded rotating log**: Appends sync events to `sync.log` in the configured data directory (`COPYQMAC_DATA_DIR` or default app support), capped at 1 MB with up to 2 rotated backup files.

### Stage 2b: Background Sync Folder Watcher (Delivered)

The read side enables automatic ingestion of items written by other machines (e.g. Fedora) via Syncthing:
- **FSEvents monitoring**: Watches configured tab sync folders using macOS FSEvents (no polling loops) with event debouncing and coalescing off the main thread.
- **Startup catch-up scan**: Performs an initial scan on startup so items synced while CopyQmac was closed appear automatically.
- **One-time upgrade repair**: Re-resolves imported row dates and moves rows to the unique tab that owns their backing sync folder. Rows with missing or ambiguous owners, or whose owning tab already holds the same identity or payload, stay in place and are logged in aggregate.
- **Group completeness and stability**: Requires item groups to be complete (presence of container `_copyq.dat`, text `.txt`, or media files, and absence of temporary sync files) and settled (modification time past `settleDelay`) before importing.
- **Durable echo-loop prevention that still sees edits**: Tracks every stem this application wrote, in-memory and durably in SQLite (`written_sync_stems`), keyed by `(stem, folder)` and linked to its entry id, so the same stem in another folder is still imported. A written group is skipped only while its canonical payload matches the local row; a changed payload is a remote edit of the same item and is applied through the newest-wins rule instead of being ignored. A written stem recorded for a live row is owned by the tab that maps the folder and stays suppressed even after a remap, until its entry is deleted with sync active, its tab is deleted, or its folder loses its last mapping. Legacy stems without a tab owner are released once at open or when their folder becomes mapped: one whose entry is gone is released, while a null-owner one that neither content-verified recovery nor the base-name/timestamp proximity matcher can link is released only while the folder is readable, so old folder history can still import; resolving a row may link an unowned stem whose complete group payload matches exactly one row in the tab (a moved creation time before the upgrade).
- **Content changes update in place**: Uses canonical SHA-256 flavour hashing to ensure re-scans and restarts are idempotent no-ops. Ownership is data: a stem's owner is the entry carrying its `application/x-copyq-itemsync-base-name` flavour, the row `written_sync_stems.entry_id` names for a locally written stem in the same tab, or a legacy row whose original creation time matches the stem stamp; an action that resolves a legacy match records it in `written_sync_stems` before it can move the row's creation time, while reporting paths stay read-only. An unchanged external file refreshes its owner's date; a group this app wrote for the owner never moves the date, so a manual import cannot reorder a locally edited item. A same-stem rewrite with different content is resolved by timestamp: a newer upstream group replaces the row's flavours in place, an older one is discarded and logged with a payload summary (formats, byte length, and a short hash, never the clipboard text), and the winning local version is written back. Content-identical stems collapse into one entry (fingerprints stored by older builds are not backfilled). See [Sync folder watcher](architecture.md#sync-folder-watcher-stage-2b) for the ownership, update, legacy-row, and cleanup rules, and [Duplicate collapsing](architecture.md#duplicate-collapsing) for the exact outcome.
- **Settled upstream deletion**: A tracked group that disappears is recorded on the first absent scan and acted on only after a later settled rescan with no in-flight Syncthing file. The matching entry is removed unless it carries a local edit that has never been written to the sync folder, and its payload is archived in the app trash first. A local edit is written back to the folder on the next sync, so it no longer permanently blocks a remote deletion.
- **Internal bookkeeping items are skipped**: An item that carries only our own bookkeeping markers (no payload, note, or pin) is not content. Import skips it without creating an entry, and one aggregate log line per scan reports the count. Backups and sync-folder writes similarly leave such entries out, so an empty item cannot travel to the other device and sync back.
- **Configuration**: Every tab with a non-empty sync folder is watched, with no per-tab switch. "Pause Sync" is the only off switch. Unknown or non-item files are ignored by the fixed built-in extension table, with no user-facing ignore list.

### Stage 2d: Two-Way Content Edits

Edits now travel in both directions on top of the same file groups:
- **A local edit rewrites the entry's own group**: The entry keeps its stem and creation time, the group is regenerated with the edited content, and files from the previous content that the new version no longer produces are removed. When content-equal adoption left the row owning more than one group, the rewrite keeps one stem and moves the extra groups to the app trash. The other machine therefore updates the same item in place instead of seeing a deletion plus a new item. A tab without a sync folder, or an unreadable folder, still saves the edit locally; the failure is logged and reported.
- **An upstream edit updates the local row in place**: A changed group for a known stem is compared by timestamp. A newer upstream edit replaces the row's flavours, note, and pinned state while keeping its id, tab, and creation time (unless upstream is later); an older one is discarded, recorded in the sync log with a payload summary (formats, byte length, and a short hash, never the clipboard text) of what lost, and the local version is written back so both machines converge.
- **Notes and pins sync with the item**: A note change writes CopyQ's `_note.txt` and a pin change its `_copyq.dat` marker, even when the content itself did not change; the other machine applies them through the same newest-wins rule. Metadata written by the sync itself matches the row's canonical payload, so it is an echo and never written back or imported twice.
- **No permanent local-edit veto**: The old rule that a locally edited entry could never be overwritten is gone. `sync_updated_at` records the version the row reflects, and the newest timestamp wins in both directions. The local-edit marker is cleared as soon as the edited version is written to the folder or the row adopts an upstream version, so it only marks an edit that has not reached the folder yet.

### Stage 2c: Two-Way Deletion Sync, Trash, and Reconciliation

Deletion is now mirrored in both directions while keeping a local recovery copy:
- **Delete in the app, remove on disk**: When an entry is deleted (single delete, Delete key, bulk delete, Clear Tab after confirmation, or eviction by the history limit) and its tab has a sync folder, every file group the entry owns (its `application/x-copyq-itemsync-base-name` stem, the stems tracked in `written_sync_stems`, or a legacy creation-time match) is moved out of the sync folder into `~/Library/Application Support/CopyQmac/trash/<timestamp>/`. Syncthing then propagates the deletion. Remove Tab unregisters the tab and leaves sync files untouched. Entries without a sync stem, and entries in tabs without a folder, leave the folder untouched. Nothing is hard-deleted, and paused sync performs no file movement; for a group this app wrote, the suppression watermark keeps the item from being re-imported when sync resumes.
- **Delete on disk, remove in the app**: The watcher tracks the stems it has seen in each watched folder. When a tracked stem vanishes, the first absent scan only records it. A later scan after `settleDelay`, with no temporary Syncthing file for that stem, removes the local owner through the same trash path. A group that is merely being rewritten reappears before that rescan and is kept. A local edit whose write-back succeeded no longer blocks removal; only an edit that never reached the folder is kept. A paused watch removes nothing.
- **Trash**: Each batch keeps the original file names plus `metadata.json` recording the stem, folder, tab id and name, reason, time, and file list. For an upstream deletion the local payload is written into the trash under its original stem instead, because the files are already gone. The trash lives outside every configured sync folder, is never synced, and File ▸ "Empty Sync Trash…" empties it only after confirmation.
- **One-shot reconciliation**: File ▸ "Reconcile Sync Folders…" reports entries without files and file groups without entries. It never runs on launch. The first dialog button is Report Only, which changes nothing; choosing Reconcile archives and removes the missing-file entries and imports the orphan groups. Reconciliation reporting does not adopt legacy owners or mutate stored flavours.
- **Per-tab comparison and resync**: The tab context menu “Compare with Sync Folder…” compares one tab with its folder. It compares every stem the row owns, so content-equal adopted groups count as matched rather than folder-only, and reports matched entries, content differences, entries without a file, folder stems without an entry, unresolved entries, and unreadable entries and files as separate counts, and counts internal-only or empty stems separately. The report stays read-only and is the default surface; a second report is identical when nothing changes. A second, explicitly confirmed action applies the same comparison: it imports folder-only stems, removes entries whose files are gone (archiving each payload to the app trash first, and keeping a row whose own archive fails while the others proceed), and updates content-different entries while keeping their id, note, and pin. It refuses to touch a row with a pending local edit, a folder item whose note or pin differs, a row whose owned groups disagree with each other or cannot all be fully decoded, or a row whose ownership rests only on the legacy creation-time rule; those are reported as conflicts. A stem that still has an in-flight temporary file, or a group that has not settled by the watcher's settle delay, is skipped until it settles instead of being imported, updated, or removed, and an update whose work is already done is reported as already in sync. The comparison's folder scan runs off the main thread. Apply is refused while sync is paused. The ownership and decoding rules are in [Per-tab comparison](architecture.md#sync-deletion-trash-and-reconciliation-stage-2c) and the identity layers in [Sync identity model](architecture.md#sync-deletion-trash-and-reconciliation-stage-2c).
